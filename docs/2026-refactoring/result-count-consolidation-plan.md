# 목록 조회 개수 공통화 작업 계획

> 조사 기준: 2026-10-10 현재 소스 코드
> 상태: 1단계 공통 컴포넌트 구현 완료 / 화면 적용 전
> 대상: 시험후기 관리, 게시글 관리, 댓글 관리, 회원 목록

## 1. 권장안

**조회 개수는 목록 제목과 같은 줄의 오른쪽에 표시한다.** 검색 영역 아래, 목록 작업 버튼 위에 고정해서 네 화면 모두 같은 순서로 읽히게 한다.

공통 컴포넌트는 숫자 표현을 담당하는 `ResultCount`와 제목·개수 배치를 담당하는 `ListResultHeader`로 나눈다. 데이터 조회와 검색 조건 관리는 기존 도메인 훅에 남긴다.

- 시험후기·게시글·댓글: `총 1,234개`
- 회원: `총 1,234명`
- 검색 후에도 같은 문구를 사용하며, 현재 적용된 조건에 맞는 서버 응답의 `totalCount`를 표시한다.
- 로딩 중에는 `조회 중…`, 개수를 알 수 없으면 `총 -개` 또는 `총 -명`을 표시한다.
- 성공 응답이 실제로 0일 때만 `총 0개` 또는 `총 0명`을 표시한다.

이 문서의 조회 개수는 **목록의 검색 결과 총개수**다. 게시글·댓글 행의 조회수(`viewCount`)와는 별개다.

| 화면                     | 개수 표시 위치                        | 현재 문구·스타일                                    | 데이터 출처                                              |
| ------------------------ | ------------------------------------- | --------------------------------------------------- | -------------------------------------------------------- |

| 게시글 `/posts/manage`   | 일괄 처리 영역 아래, 테이블 위 왼쪽   | `총 N개의 게시물`, 12px, 파란 숫자 강조, 미응답은 0 | `PostTable` → `usePostTableState` → `usePostList`        |

| 회원 `/member/info`      | 목록 제목 아래, 회원 작업 버튼 오른쪽 | `총 N명`, 14px, 회색, 초기값 0                      | `MemberDirectorySection` → `useMemberDirectoryState`     |

현재 문제는 다음과 같다.

1. 위치, 문구, 숫자 색상과 크기가 달라 같은 정보라는 인상이 약하다.
2. 게시글·댓글은 `totalCount ?? 0`, 회원은 상태 초깃값 0을 사용해 아직 응답이 없는데도 빈 결과처럼 보일 수 있다.
3. 회원은 검색 조건을 바꿔도 응답 전까지 이전 개수를 유지한다. 새 조건과 이전 숫자가 함께 표시될 수 있다.
4. `PostFilterPanel`, `CommentFilterPanel`에는 별도의 `totalCount` prop과 개수 JSX가 남아 있다. 현재 페이지는 이 prop을 전달하지 않아 표시되지 않지만, 나중에 전달하면 중복 표시가 생긴다.
5. 숫자 포맷의 locale이 일부만 `ko-KR`로 명시되어 있다.

## 3. 표시 위치와 시각 규칙

### 3.1 네 화면의 공통 배치

```text
[페이지 제목 / 설명]

[검색 영역]

시험후기 목록                                  총 1,234개
[테이블]
[페이지네이션]
```

작업 버튼이 있는 화면은 제목·개수 아래에 버튼을 배치한다.

```text
게시글 목록                                    총 1,234개
[선택한 게시글 일괄 처리 버튼 — 선택했을 때 표시]
[테이블]
[페이지네이션]

회원 목록                                      총 1,234명
[포인트 지급 / 제재 부여 / 회원 탈퇴 / 알림 전송]
[테이블]
[페이지네이션]
```

목록 제목과 개수를 묶으면 개수가 어떤 목록의 결과인지 바로 알 수 있다. 버튼의 표시 여부가 바뀌어도 개수 위치는 유지된다. 필터 패널은 조건 입력을, 목록 헤더는 적용 결과를 보여 주므로 검색 전 입력값과 현재 결과도 구분하기 쉽다.

### 3.2 세부 규칙

| 요소               | 권장 규칙                                                             |
| ------------------ | --------------------------------------------------------------------- |
| 헤더               | `flex min-w-0 flex-wrap items-center justify-between gap-x-4 gap-y-1` |
| 목록 제목          | 기존 `h2`, `text-lg font-bold` 유지                                   |
| 개수               | `text-sm text-muted-foreground whitespace-nowrap`                     |
| 숫자               | `font-semibold text-foreground tabular-nums`                          |
| 숫자 구분          | `toLocaleString('ko-KR')`                                             |
| 간격               | 헤더·작업 영역·테이블을 `gap-3`으로 배치                              |
| 좁은 화면          | 한 줄이 부족하면 개수를 다음 줄에 배치하고 왼쪽 정렬                  |
| 테이블 가로 스크롤 | 헤더는 스크롤 컨테이너 밖에 배치해 개수가 함께 밀리지 않게 함         |

개수는 일반 텍스트로 표현한다. 숫자가 상태나 작업을 뜻하지 않으므로 상태 배지나 버튼 모양은 사용하지 않는다.

## 4. 공통 컴포넌트 설계

### 4.1 파일과 역할

| 제안 파일                                    | 역할                                       |
| -------------------------------------------- | ------------------------------------------ |
| `src/shared/components/ResultCount.tsx`      | 개수 문구, 단위, 숫자 포맷, 조회 상태 표현 |
| `src/shared/components/ListResultHeader.tsx` | `h2` 제목과 `ResultCount`의 배치           |
| `src/shared/components/index.ts`             | 두 컴포넌트 export                         |

개수 표현과 헤더 배치를 분리하면 이후 제목이 없는 작은 목록에서도 `ResultCount`를 재사용할 수 있다. 공통 컴포넌트에는 API 호출, 검색 조건 해석, 페이지 계산, 선택 개수 관리를 넣지 않는다.

### 4.2 제안 props

아래 타입은 1단계 공통 컴포넌트에 적용한 계약이다.

```ts
type ResultCountProps = {
  totalCount: number | undefined;
  unit?: '개' | '명' | '건'; // 기본값: '개'
  status: 'loading' | 'ready' | 'error';
};

type ListResultHeaderProps = ResultCountProps & {
  title: string;
  titleId?: string; // section의 aria-labelledby와 연결
};
```

`totalCount`와 `status`는 호출부에서 전달한다. 공통 UI가 `undefined`를 0으로 변환하거나 행 배열 길이로 개수를 추정하지 않게 한다. 도메인별 색상·문구 override는 첫 적용 범위에서 제공하지 않아 표현이 다시 분산되는 것을 막는다.

### 4.3 상태 정책

| 입력 상태                       | 표시                        | 의미                                               |
| ------------------------------- | --------------------------- | -------------------------------------------------- |
| `loading`                       | `조회 중…`                  | 최초 조회, 페이지·정렬·조건 변경, 재조회가 진행 중 |
| `ready`, `totalCount=1234`      | `총 1,234개` / `총 1,234명` | 현재 조회 결과 총개수                              |
| `ready`, `totalCount=0`         | `총 0개` / `총 0명`         | 성공 응답의 빈 결과                                |
| `ready`, `totalCount=undefined` | `총 -개` / `총 -명`         | 총개수 정보가 없는 결과                            |
| `error`                         | `개수 확인 불가`            | 현재 조회 실패, 이전 숫자도 숨김                   |

오류를 우선하고, 다음으로 진행 중 상태, 마지막으로 성공 응답을 판단한다. 이전 조회 오류가 남은 채 재시도 중이면 현재 요청의 진행 상태를 기준으로 `loading`을 전달한다.

이번 범위에서는 모든 재조회 동안 숫자를 잠시 숨기는 단순 정책을 권장한다. 이전 개수 유지와 검색 조건별 캐시 보관을 새로 구현할 필요가 없고, 이전 조건의 숫자가 현재 결과로 오인되는 문제도 피할 수 있다.

개수 영역에 `role="status"`와 `aria-atomic="true"`를 적용해 갱신을 정중하게 알린다. 영역은 상태가 바뀌어도 마운트를 유지하고, 별도 중복 `aria-label` 없이 화면 문구를 읽게 한다. `h2`는 기존 목록 섹션과 연결한다.

## 5. 데이터와 제목 소유권

### 5.1 데이터 기준

- `totalCount`는 현재 조건으로 조회한 **전체 결과 수**다. 현재 페이지의 `data.length`, `currentCount`, `totalPage`, 선택한 행 수를 사용하지 않는다.
- 댓글은 일반 목록과 `parentId` 기반 대댓글 목록 중 현재 활성 조회의 개수를 사용한다. 상태도 같은 활성 조회에서 가져온다.
- 삭제·복구·공개 상태 변경 후에는 기존 재조회 흐름에서 받은 새 응답을 사용한다. UI에서 임의로 개수를 더하거나 빼지 않는다.
- 회원 상세 수정 후에도 기존 목록 재조회 결과를 반영한다.

### 5.2 기존 조회 위치를 유지한다

시험후기·게시글·댓글은 개수를 소유한 테이블 컴포넌트 안에서 `ListResultHeader`를 렌더링한다. 페이지의 기존 `h2`를 테이블로 옮겨 제목이 두 번 나타나지 않게 한다. 페이지의 목록 `section`은 유지하고 `aria-labelledby`로 새 제목과 연결한다.

이렇게 하면 개수를 페이지까지 올리기 위한 콜백, 추가 상태, 중복 API 요청이 필요 없다. 현재 세 테이블이 조회와 페이지네이션까지 포함한 목록 컨테이너라는 구조에도 맞는다.

회원은 `MemberDirectorySection`이 이미 제목과 데이터를 함께 받으므로 기존 `h2`와 개수 span을 공통 헤더로 교체한다. 기존 제목 ID를 `titleId`로 전달한다.

### 5.3 조회 상태 전달 보완

| 도메인   | 필요한 보완                                                                                                                                                                                                   |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 시험후기 | `useExamReviews`의 조회 오류와 `isFetching`을 `ExamTable`에서 사용한다. `data` prop으로 조회를 끄는 경우 요청 상태가 아닌 전달 데이터 기준으로 `ready`를 사용한다. 총개수 메타데이터가 없으면 `-`로 표시한다. |
| 게시글   | `usePostList`에서 `isFetching`을 반환하고 `usePostTableState`를 거쳐 전달한다. 기존에 반환하는 `error`도 활용한다.                                                                                            |
| 댓글     | 일반 댓글·대댓글 쿼리의 `isFetching`과 오류를 `useCommentTableState`에서 현재 활성 조회 기준으로 선택해 반환한다.                                                                                             |
| 회원     | `totalCount` 초깃값을 `undefined`로 바꾸고 관련 prop 타입을 수정한다. 목록 조회 오류 상태를 훅에서 관리하고 페이지를 거쳐 전달한다. 기존 `isListLoading`과 최신 요청 ID 보호 로직은 활용한다.                 |

`isLoading`만 사용하면 데이터가 있는 상태의 재조회는 감지되지 않을 수 있으므로 쿼리 기반 화면은 `isFetching`도 확인한다. 회원은 아직 응답이 없는 첫 렌더에서 `ready + undefined`로 `-`가 보이더라도 0으로 처리하지 않는다. 새 요청 시작 시 오류 상태를 해제하고, 최신 요청만 오류·성공·로딩 상태를 갱신하도록 한다.

검증 시 조회 지연과 실패를 재현해 상태 전환을 확인한다. 테스트를 위해 운영 데이터의 삭제나 수정은 수행하지 않는다.

## 7. 완료 기준과 범위

완료 기준은 네 화면에서 목록 제목 오른쪽에 개수가 한 번만 표시되고, 문구·단위·로딩·오류 정책을 같은 컴포넌트로 처리하는 것이다. 목록 제목의 `h2` 의미와 섹션 연결, 기존 검색·선택·페이지네이션 동작도 유지되어야 한다.

다음 항목은 이번 작업 범위에서 제외한다.

- 게시글·댓글 행의 조회수, 추천 수, 신고 수
- 상세 화면의 댓글 목록, 신고 집계, 회원 제재 이력의 개수 표시
- 선택한 행 수 표시와 회원 작업 버튼 기능 구현
- API 응답 계약, 페이지네이션 계산, 검색 훅 전체 구조 변경
- 테이블 로딩·빈 상태 UI 전체 공통화

관련 기존 계획: [페이지네이션 공통화](./pagination-consolidation-plan.md), [페이지 레이아웃 정렬](./page-layout-alignment-plan.md).
