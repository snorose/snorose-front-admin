# 프론트엔드 구조 점검 보고서

> 점검일: 2026-08-17  
> 대상 브랜치: `dev`  
> 대상 프로젝트: `snorose-front-admin`

## 1. 문서 목적

이 문서는 현재 프론트엔드 프로젝트가 어떤 구조로 구성되어 있고, 화면과 데이터가 어떻게 연결되는지 설명한다.

또한 현재 구조의 장점과 기술 부채를 구분하고, 이후 리팩터링을 진행할 때 참고할 수 있도록 개선 우선순위를 정리한다.

## 2. 한눈에 보는 현재 상태

현재 프로젝트는 React와 TypeScript를 기반으로 한 관리자 웹 애플리케이션이다. 페이지, 비즈니스 도메인, 공통 코드, API 호출을 분리한 **도메인 중심 구조**를 사용하고 있다.

전반적인 기반은 안정적이다.

- TypeScript의 `strict` 설정을 사용한다.
- ESLint, Prettier, Husky, lint-staged가 구성되어 있다.
- TanStack Query를 이용한 서버 상태 관리 기반이 있다.
- 공통 UI와 비즈니스 UI가 대체로 분리되어 있다.
- ESLint, 테스트, 프로덕션 빌드가 모두 통과한다.

다만 기능별로 구현 방식이 달라지면서 다음 문제가 나타나고 있다.

1. 인증 관련 모듈에 순환 의존이 있다.
2. `shared`, `apis`, `domains` 사이의 의존 방향이 일정하지 않다.
3. 모든 페이지가 초기 번들에 포함되어 번들 크기가 크다.
4. 일부 페이지와 컴포넌트가 너무 많은 책임을 담당한다.
5. 존재하지 않는 경로와 런타임 오류를 처리하는 화면이 연결되어 있지 않다.
6. 테스트는 통과하지만 주요 관리 기능에 대한 테스트가 부족하다.

## 3. 기술 구성

| 구분        | 사용 기술               |
| ----------- | ----------------------- |
| UI          | React 19, TypeScript    |
| 라우팅      | React Router            |
| 서버 상태   | TanStack Query          |
| HTTP 통신   | Axios                   |
| 스타일      | Tailwind CSS 4          |
| UI 기반     | shadcn/ui, Radix UI     |
| 테이블      | TanStack Table          |
| 빌드        | Vite                    |

Redux나 Zustand와 같은 별도 전역 상태 라이브러리는 사용하지 않는다. 인증 상태는 React Context로 관리하고, 나머지 화면 상태는 각 페이지나 도메인 훅에서 관리한다.

## 5. 애플리케이션 실행 구조

애플리케이션은 다음 순서로 구성된다.

```text
main.tsx
  └─ App.tsx
      ├─ QueryClientProvider
      ├─ BrowserRouter
      ├─ AuthProvider
      ├─ Toaster
      └─ Routes
          ├─ 로그인 화면
          └─ ProtectedRoute
              └─ Sidebar + 관리자 페이지
```

### 일반적인 데이터 흐름

구조가 잘 적용된 기능에서는 다음 흐름을 사용한다.

```text
Page
  → Domain Component
    → Domain Query Hook
      → API Function
        → Axios Instance
          → Backend API
```

예를 들어 게시글 목록은 페이지가 필터와 URL 상태를 관리하고, 도메인 컴포넌트와 Query 훅이 조회 상태를 담당한다.

하지만 회원 관리와 일부 시험 후기·포인트 기능은 페이지, 컴포넌트 또는 일반 훅에서 API를 직접 호출한다. 따라서 현재는 하나의 데이터 흐름으로 완전히 통일된 상태가 아니다.

## 6. 현재 구조의 장점

### 6.1 페이지와 비즈니스 기능이 분리되어 있다

`pages`는 라우트 단위 화면을 담당하고, 실제 테이블·필터·다이얼로그 등의 기능은 `domains`에서 관리한다. 페이지가 단순 조합 역할만 하는 경우에는 화면 구조를 이해하기 쉽다.

### 6.2 공통 UI 기반이 잘 구성되어 있다

버튼, 입력창, 다이얼로그, 테이블과 같은 기본 UI가 `shared/components/ui`에 모여 있다. 이를 기반으로 도메인 컴포넌트를 만들기 때문에 화면 스타일을 통일하기 쉽다.

### 6.3 타입과 빌드 설정이 엄격하다

TypeScript의 `strict`, `noUnusedLocals`, `noUnusedParameters` 등이 활성화되어 있다. 사용하지 않는 코드나 잘못된 타입을 빌드 단계에서 비교적 빠르게 발견할 수 있다.

### 6.4 서버 상태 관리 기반이 있다

게시글, 댓글, 문의 등에서는 TanStack Query의 조회, 변경, 캐시 무효화 패턴을 사용한다. 이 패턴을 다른 도메인에도 확장하면 상태 관리 방식을 통일할 수 있다.

## 7. 주요 점검 결과

### 7.1 인증 모듈의 순환 의존

현재 인증과 토큰 재발급 코드는 다음과 같은 정적 의존 관계를 가진다.

```text
shared/axios/instance.ts
  → shared/utils/index.ts
    → shared/utils/token-manager.ts
      → apis/index.ts
        → apis/auth.ts
          → shared/axios/instance.ts
```

즉, Axios 인스턴스를 만드는 도중 토큰 관리자가 API 모듈을 불러오고, API 모듈이 다시 Axios 인스턴스를 불러온다.

현재 빌드와 실행 초기화는 통과하지만 다음 위험이 있다.

- 모듈 로딩 순서가 바뀌면 초기화되지 않은 값을 참조할 수 있다.
- 인증 코드 수정 시 예상하지 못한 영역에 영향을 줄 수 있다.
- `apis/index.ts`가 모든 API를 다시 export하므로 인증 초기화 과정에서 불필요한 API 모듈까지 연결된다.

#### 권장 방향

1. 토큰 재발급 요청은 인증 인터셉터가 없는 별도 HTTP 클라이언트를 사용한다.
2. 기반 모듈에서는 `@/apis`나 `@/shared/utils` 배럴 파일 대신 필요한 파일을 직접 import한다.
3. `shared`에는 저장소, 순수 유틸, HTTP 기반 코드만 두고 인증 상태 조합은 애플리케이션 계층으로 이동한다.

### 7.2 계층 의존 방향의 불일치

현재 주요 의존 예시는 다음과 같다.

| 의존 관계          | 예시                                                | 문제점                                         |
| ------------------ | --------------------------------------------------- | ---------------------------------------------- |
| `shared → domains` | `SanctionModal`이 MemberInfo의 징계 다이얼로그 사용 | 공통 계층이 특정 도메인에 종속됨               |
| `shared → apis`    | AuthProvider, token-manager, MemberInfoPopover      | 공통 계층의 재사용성과 독립성이 낮아짐         |
| `apis → domains`   | reviews, posts, comments API가 도메인 타입 사용     | API와 도메인이 서로 참조할 가능성이 생김       |
| `domains → apis`   | 도메인 훅과 컴포넌트에서 API 호출                   | 위 관계와 합쳐지면 순환 구조가 쉬워짐          |
| `pages → apis`     | 일부 페이지에서 API 직접 호출                       | 페이지가 화면 조합과 데이터 통신을 함께 담당함 |

권장 의존 방향은 아래처럼 단방향으로 유지하는 것이다.

```text
App / Router
  → Pages
    → Domains
      → API Client
        → Shared Infrastructure
```

`shared`는 상위 계층을 참조하지 않아야 한다. 도메인 타입은 해당 도메인이 소유하고, API도 도메인 내부에 함께 둘지 최상위 `apis`에서 관리할지 하나의 규칙을 선택해야 한다.

현재 구조에서는 한 번에 전체 폴더를 이동하기보다 다음 규칙부터 적용하는 편이 안전하다.

- 새 API 호출은 도메인 Query/Mutation 훅을 통해 사용한다.
- 페이지에서는 API 함수를 직접 import하지 않는다.
- `shared`에서 `domains`를 import하지 않는다.
- 배럴 import로 순환 관계가 생기는 기반 코드에서는 직접 경로를 사용한다.

### 7.3 서버 상태 관리 방식의 불일치

게시글, 댓글, 문의는 주로 TanStack Query를 사용한다. 반면 회원 목록은 `useEffect`, `useState`, 직접 API 호출로 로딩·오류·캐시를 관리한다.

이 방식이 기능적으로 잘못된 것은 아니지만, 프로젝트 내부에서 다음 차이가 생긴다.

- 로딩과 오류 처리 방식이 도메인마다 다르다.
- 캐시 무효화와 새로고침 방법이 달라진다.
- 중복 요청 방지와 이전 요청 취소를 직접 처리해야 한다.
- 테스트 작성 방식도 달라진다.

서버에서 가져오는 목록과 상세 정보는 가능하면 Query 훅으로 통일하고, 입력값·모달·선택 상태처럼 화면에만 필요한 값은 로컬 상태로 유지하는 것을 권장한다.

### 7.4 초기 번들 크기

프로덕션 빌드 결과는 다음과 같다.

| 파일       |      크기 |     gzip |
| ---------- | --------: | -------: |
| JavaScript | 약 1.40MB | 약 424KB |
| CSS        |  약 106KB |  약 18KB |

Vite는 500KB를 초과한 JavaScript 청크에 대해 경고를 출력한다.

주요 원인은 다음과 같다.

- `App.tsx`에서 모든 페이지를 정적으로 import한다.
- 엑셀 업로드 페이지가 큰 `xlsx` 라이브러리를 사용한다.
- 관리자 기능 전체가 하나의 초기 JavaScript 청크에 포함된다.

#### 권장 방향

- 라우트 단위로 `React.lazy`와 `Suspense`를 적용한다.
- `xlsx`는 엑셀 페이지 진입 또는 파일 처리 시점에 동적으로 import한다.
- 번들 분석 후 공통 라이브러리 분리가 필요한지 판단한다.

라우트 분리만 적용해도 로그인과 일반 관리 화면의 초기 로딩에서 엑셀 관련 코드를 제외할 수 있다.

### 7.5 큰 파일과 책임 집중

다음 파일은 여러 책임을 동시에 처리하고 있어 변경 영향 범위가 크다.

| 파일                           | 줄 수 | 포함된 주요 책임                                    |
| ------------------------------ | ----: | --------------------------------------------------- |
| `ExcelPointUploadPage.tsx`     |   915 | 엑셀 파싱, 검증, API 요청, 결과 표시, 파일 다운로드 |
| `ExamDetailSection.tsx`        |   799 | 상세 표시, 수정, 삭제, 상태 변경, 여러 패널 조합    |

파일 크기 자체가 문제라기보다 서로 다른 변경 이유가 하나의 파일에 모여 있다는 점이 중요하다.

예를 들어 엑셀 업로드 화면은 다음과 같이 나눌 수 있다.

```text
ExcelPointUploadPage
├── useExcelPointUpload          # 전체 화면 상태와 요청 흐름
├── excel-point-parser           # 엑셀 헤더와 행 파싱
├── excel-point-validator        # 입력값 검증
├── ExcelUploadForm              # 파일과 지급 조건 입력
├── ExcelPreviewTable            # 업로드 전 미리보기
└── ExcelUploadResult            # 성공·실패 결과
```

### 7.6 라우팅과 오류 처리

현재 인증된 관리자 영역 내부에는 존재하지 않는 경로를 처리하는 fallback 라우트가 없다. 따라서 잘못된 주소로 접근하면 사이드바만 있고 본문은 비어 있는 화면이 표시될 수 있다.

추가로 확인된 항목은 다음과 같다.

- `PATHS.LOGIN`은 `/login`으로 선언되어 있지만 실제 로그인 라우트는 `/`이다.
- `PATHS.POINT_HISTORY`는 선언되어 있지만 연결된 라우트가 없다.
- `ErrorBoundary.tsx`가 존재하지만 애플리케이션에 연결되어 있지 않다.
- 404, 500 이미지 자산은 있지만 전용 오류 라우트가 없다.

#### 권장 방향

- 공개 라우트와 인증 라우트를 명확히 나눈다.
- 관리자 레이아웃을 별도 컴포넌트 또는 중첩 라우트의 `Outlet` 구조로 분리한다.
- 마지막에 `*` 경로를 추가해 404 화면을 제공한다.
- 루트 Provider 영역에 ErrorBoundary를 연결한다.
- 경로 상수와 실제 라우트를 일치시킨다.

### 7.7 테스트 현황

현재 테스트 결과는 다음과 같다.

- 테스트 파일: 5개
- 테스트 케이스: 70개
- 결과: 전체 통과

테스트가 있는 주요 영역은 로그인, 푸시 알림, 시험 후기 일부, 포인트 동결 목록이다.

다만 푸시 알림 테스트 실행 중 비동기 상태 변경이 `act(...)`로 감싸지지 않았다는 React 경고가 반복된다. 테스트가 통과하더라도 비동기 상태가 완전히 반영되기 전에 검증이 끝날 가능성이 있으므로 정리하는 것이 좋다.

회원, 게시글, 댓글, 문의 도메인은 코드 규모에 비해 테스트가 적거나 없다. 모든 UI를 테스트하기보다 다음 흐름을 우선하는 편이 효과적이다.

1. 권한과 토큰 재발급
2. 목록 검색 조건과 URL 동기화
3. 삭제·복구·상태 변경 후 Query 캐시 갱신
4. 엑셀 행 파싱과 검증
5. 잘못된 경로와 API 오류 화면

### 7.8 기타 정리 대상

- `MemberInfoTablePagenation.tsx`의 `Pagenation`은 `Pagination`으로 수정할 필요가 있다.
- 게시글 상세와 문의 상태에는 아직 API 연동 예정 TODO가 남아 있다.
- 일부 이벤트 핸들러에 개발용 `console.log`가 남아 있다.
- `src/components`에는 ErrorBoundary만 있으며, 공통 컴포넌트 위치 규칙과 다르다.

## 8. 권장 목표 구조

현재 구조를 유지하면서 의존 방향을 명확히 하면 다음과 같은 형태로 정리할 수 있다.

```text
src/
├── app/
│   ├── App.tsx
│   ├── router.tsx
│   └── providers.tsx
├── pages/
├── domains/
│   └── Feature/
│       ├── api/
│       ├── components/
│       ├── hooks/
│       ├── types/
│       ├── constants/
│       └── utils/
└── shared/
    ├── api/               # Axios 기반 클라이언트
    ├── components/
    │   └── ui/
    ├── hooks/
    ├── types/
    └── utils/
```

핵심은 폴더 이름보다 다음 의존 규칙이다.

```text
app → pages → domains → shared
```

- 오른쪽 계층은 왼쪽 계층을 import하지 않는다.
- 한 도메인은 가능한 한 다른 도메인의 내부 파일을 직접 import하지 않는다.
- 페이지는 API 세부 구현을 알지 않는다.
- 서버 상태는 도메인 Query/Mutation 훅을 통해 접근한다.
- `shared`에는 특정 업무 도메인 지식이 들어가지 않는다.

## 9. 개선 우선순위

### 1단계: 안정성 정리

| 작업                        | 이유                              |
| --------------------------- | --------------------------------- |
| 인증 순환 의존 제거         | 초기화 순서와 인증 장애 위험 감소 |
| 404 fallback 라우트 추가    | 잘못된 경로에서 빈 화면 방지      |
| ErrorBoundary 연결          | 예기치 않은 렌더링 오류 대응      |
| 테스트 `act(...)` 경고 제거 | 테스트 신뢰도 향상                |
| 사용하지 않는 PATHS 정리    | 실제 라우트와 상수 일치           |

### 2단계: 성능과 경계 정리

| 작업                         | 이유                                       |
| ---------------------------- | ------------------------------------------ |
| 라우트 lazy loading          | 초기 번들 크기 감소                        |
| `xlsx` 동적 import           | 엑셀 기능을 사용하지 않을 때 다운로드 방지 |
| `shared → domains` 의존 제거 | 계층 방향 회복                             |
| API 타입 소유 위치 통일      | 도메인과 API 사이 결합 감소                |

### 3단계: 상태 관리 통일

| 작업                               | 이유                              |
| ---------------------------------- | --------------------------------- |
| 회원 목록·상세를 Query 훅으로 전환 | 로딩, 오류, 캐시 처리 일관성 확보 |
| Query Key 규칙 정의                | 캐시 무효화 실수 방지             |
| 페이지의 직접 API 호출 제거        | 페이지 책임 축소                  |

### 4단계: 큰 기능 분리와 테스트 확대

| 작업                      | 이유                       |
| ------------------------- | -------------------------- |
| 엑셀 업로드 페이지 분리   | 파싱·검증 로직 테스트 용이 |
| 시험 후기 상세·검색 분리  | 변경 영향 범위 감소        |
| 핵심 Mutation 테스트 추가 | 관리자 작업의 회귀 방지    |

## 10. 문서 운영 체크리스트

이 문서는 리팩터링이 끝난 뒤에도 계속 유지하는 상시 문서가 아니라, 현재 구조를 점검하고 후속 작업을 정리하기 위한 기준 문서다.

권장 흐름은 다음과 같다.

```text
점검 문서 검토·병합
  → 항목별 이슈와 작은 구현 PR 진행
    → 유효한 내용을 상시 아키텍처 문서로 이전
      → 완료된 점검·제안 문서 정리
```

### 문서 검토와 작업 진행

- [ ] Draft PR에서 현재 구조와 문제점의 사실관계 확인
- [ ] 리팩터링 우선순위와 공통화 경계에 대한 리뷰 의견 반영
- [ ] 검토가 끝난 문서 PR을 `Ready for review`로 전환한 뒤 문서만 병합
- [ ] 리팩터링 항목을 독립적인 이슈와 작은 구현 PR로 분리
- [ ] 각 작업이 끝날 때 관련 이슈와 PR 링크 및 진행 상태 갱신

### 모든 리팩터링 완료 후

- [ ] 계속 유효한 현재 구조와 의존 규칙을 `docs/architecture.md`와 같은 상시 문서로 이전
- [ ] 장기 보존이 필요한 설계 결정을 ADR 또는 관련 이슈·PR에 기록
- [ ] 더 이상 유효하지 않은 수치, 문제점, 제안이 남아 있지 않은지 확인
- [ ] 고유한 내용이 모두 이전되면 `architecture-review.md`와 `refactoring-opportunities.md`를 삭제하거나 `완료됨`·`대체됨` 상태로 표시
- [ ] 마지막 정리 PR에 기존 점검 문서와 주요 구현 PR 링크를 남겨 Git 이력에서 추적 가능하도록 정리

## 12. 결론

현재 프로젝트는 페이지, 도메인, 공통 코드를 구분한 좋은 기반을 갖고 있으며 정적 검사와 빌드도 정상적으로 통과한다.

가장 먼저 해결할 부분은 **인증 순환 의존**이다. 이후 **라우트 단위 코드 분할**, **계층 의존 방향 통일**, **서버 상태 관리 방식 통일** 순으로 개선하는 것이 안전하다.

대규모 폴더 이동부터 시작하기보다는 새 코드에 의존 규칙을 적용하고, 변경이 잦거나 위험도가 높은 기능부터 단계적으로 이전하는 방식을 권장한다.
