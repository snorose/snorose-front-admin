# FAQ 관리

## 구현 범위

- 문의 및 신고 → FAQ 관리 (`/report/faq`)
- 목록 조회, 작성, 수정, 확인 후 삭제를 실제 API 클라이언트에 연결한다.
- 공통 헤더, 테이블, 입력 컴포넌트, 모달, 페이지네이션, URL 페이지 훅, Axios 인스턴스와 오류 유틸을 재사용한다.
- 별도 목 데이터나 유저단 FAQ의 자동 이관은 추가하지 않는다.

## API 계약

기준: 작업 공간 `docs/admin/faq/`의 목록 조회·작성·수정·삭제 PDF 4개. 유저 UI는 `snorose-front`의 #2050 변경이 반영된 PR [#2088](https://github.com/snorose/snorose-front/pull/2088), `origin/feat/support`의 FAQ 코드도 확인했다. 원격에 `feat/#2050-faq` 브랜치는 현재 없으며, 해당 변경은 커밋 `7e1a692e`에서 확인할 수 있다.

| 기능 | 요청                                   | 응답 result                |
| ---- | -------------------------------------- | -------------------------- |
| 목록 | `GET /v1/admin/support/faq?page=0`     | `{ hasNext, data: Faq[] }` |
| 작성 | `POST /v1/admin/support/faq`           | `{ faqId }`                |
| 수정 | `PATCH /v1/admin/support/faq/{faqId}`  | `{ faqId }`                |
| 삭제 | `DELETE /v1/admin/support/faq/{faqId}` | `{ faqId }`                |

작성·수정 요청은 `{ category, question, answer }`이다. 목록 응답의 분류 필드명은 `faqCategory`이며, ID는 게시글 ID와 별개의 `faqId`이다. 작성자와 작성·수정일은 목록 응답을 그대로 표시한다.

목록은 서버 응답 순서를 유지한다. API에 전체 개수와 전체 페이지 수가 없어 `hasNext`가 끝날 때까지 전체 목록을 조회한 뒤 10개씩 나눈다. 실제 전체 건수와 공통 `PaginationBar`의 기본 번호형 페이지네이션을 사용한다. 서버 페이지 조회가 실패하거나 같은 페이지가 반복되면 부분 목록을 성공으로 표시하지 않는다. 저장 후 모든 FAQ 목록 캐시를 무효화한다. 조회 실패는 빈 목록과 구분하며 재조회할 수 있다. 저장 실패 시 작성 내용을 보존한다.

## 현재 UI에서 정한 사항과 확인할 사항

- 분류는 새 유저 FAQ의 `가입 · 인증`, `시험후기`, `포인트`, `게시판 · 커뮤니티`, `기능 이용`, `스노로즈 운영` 6개 중 선택한다. `전체`는 조회 전용이므로 작성 옵션에 포함하지 않는다. 기존 데이터에 다른 분류가 있으면 수정 시 해당 값을 보존할 수 있도록 함께 표시한다.
- 화면의 질문·답변 명칭은 제목·내용으로 표시하며 API의 `question`·`answer` 필드명은 유지한다. 행을 누르면 제목 열부터 작성자 열까지 두 열 너비로 텍스트 내용이 펼쳐지고, 수정·삭제 버튼은 내용 아래 오른쪽에 정렬한다. 긴 제목은 접힌 상태에서 말줄임하고 펼친 상태에서는 줄바꿈으로 전체를 표시한다. 별도 하단 상세 패널이나 내용 라벨은 표시하지 않는다. 다른 행을 선택하거나 페이지를 이동하면 이전 펼침 상태를 해제한다.
- 분류·제목·내용의 빈 값과 공백만 있는 값을 막는다. 문서에 최대 길이가 없어 임의의 길이 제한은 두지 않는다.
- 사용자가 유저 화면에 맞춰 텍스트 유지로 결정했다. `answer`는 문자열 그대로 저장하며, 공지의 HTML 기반 Tiptap 편집기와 HTML·Markdown 렌더링은 적용하지 않는다.
- 작성 중 이탈은 기존 공지와 같은 React Router `useBlocker`로 확인한다. 계속 작성하면 입력을 유지하고 취소를 확정해야 이동한다. 저장 중에는 이탈 확정을 막고, 저장 성공 후의 목록 이동은 허용한다. 문서 새로고침·닫기는 `beforeunload`로 보호한다.
- 이전 유저단의 `content[]`는 소제목·목록·별도 링크를 가진 구조다. 새 문자열 답변으로 이관할 때 표현을 보존하는 규칙과 기존 9개 FAQ의 카테고리 지정이 필요하다.
- 삭제는 API가 제공되어 개별 확인 모달과 함께 지원한다. 공개 여부·순서 변경 필드와 API는 없어 제공하지 않는다.
- 서버의 정렬 기준과 신규 항목의 위치는 문서에 없다. 작성 후 첫 페이지로 돌아가지만 신규 항목이 첫 행에 표시된다고 가정하지 않는다.
- FAQ 응답에는 작성자의 회원 ID가 없어 현재는 `writer`를 일반 텍스트로 표시한다. 회원 검색 연결은 제공하지 않으며 공통 `MemberInfoPopover`와 회원 관리 화면도 변경하지 않는다. 추후 작성자 `encryptedUserId`가 응답에 추가되면 기존 공통 컴포넌트에 ID와 표시명을 전달해 회원 정보 메뉴를 연결할 수 있다.
- 현재 로컬 유저단의 작업 브랜치(`feature/#2102-event-update`)에는 이전 하드코딩 FAQ가 남아 있다. #2050이 반영된 `feat/support`는 `GET /v1/support/faq?category=...`를 호출하고 `{faq.answer}`를 그대로 표시한다. HTML·Markdown·URL 자동 링크 처리는 없다. 이 어드민 작업에서 유저단 코드는 수정하지 않는다.

## 검증

API 계약 테스트와 화면 통합 테스트에서 페이지 변환, 작성·수정·삭제, 줄바꿈·URL 보존, 저장 중 중복 요청 방지, 실패 후 재시도, 삭제 후 이전 페이지 이동을 확인한다. 실제 서버의 배포·권한·동작은 별도 개발 환경 확인 대상이다.

실제 dev API를 사용하는 E2E는 [FAQ E2E 문서](../../../../e2e/features/faqs/README.md)에 실행 명령·TC·데이터 정리·실행 결과를 기록한다. 실제 작성·수정·삭제와 API 재조회, 행 펼침, QA FAQ 11개를 생성한 번호형 페이지 이동 및 작성 중 이탈 보호를 검증했다. 작성자 텍스트 표시로 변경한 뒤 관련 단위·통합 테스트 37개와 실제 dev API 조회 E2E 12개(로그인 setup 포함)가 통과했다. 쓰기 E2E는 이번 변경에서 재실행하지 않았다.
