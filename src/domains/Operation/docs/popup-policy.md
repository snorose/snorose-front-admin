# 팝업 관리 API 연동 정책

2026-10-20 수정된 어드민 팝업 등록·수정·삭제·목록·상세 API 문서와 첨부 CSV 기준이다. 문서의 dev/prod 배포 상태는 모두 `No`이며, 실제 배포 여부는 확인하지 않았다.

## 현재 동작

- 공통 Axios 클라이언트의 인증·토큰 갱신을 사용한다.
- `GET /v1/admin/popups?page=0`: 페이지당 10개를 최신 등록순(`createdAt DESC, id DESC`)으로 조회한다. 화면 페이지 번호는 1부터 표시한다.
- `GET /v1/admin/popups/{popupId}`: 수정 다이얼로그를 열기 전에 본문과 CDN 이미지 URL을 조회한다.
- `POST /v1/admin/popups`: `request` JSON 파트(`application/json`)와 선택적인 `image` 파일 파트를 multipart로 전송한다.
- `PATCH /v1/admin/popups/{popupId}`: 변경된 필드만 JSON 파트로 전송한다. 본문 삭제는 `description: null`, 이미지 삭제는 `removeImage: true`, 이미지 교체는 파일 파트로 구분한다. 변경하지 않은 필드는 생략한다.
- `DELETE /v1/admin/popups/{popupId}`: 확인 후 서버에 삭제를 요청한다. 같은 내보내기 경로의 삭제 문서도 함께 참조했다.
- 저장·삭제 성공 후 목록 전체 쿼리를 무효화해 순서와 전체 개수를 갱신한다. 마지막 페이지의 유일한 항목을 삭제하면 이전 페이지로 이동한다.
- 조회 오류 시 재시도하고 저장 실패 시 편집 내용을 보존한다. 처리 중에는 중복 저장·삭제를 막는다.
- 이미지 선택 시 확장자·MIME·10MB 제한을 검사한다. 기존 이미지는 CDN URL, 새 이미지는 임시 URL로 미리 보고 임시 URL은 교체·닫기·화면 이탈 시 해제한다.

## 기존 프론트와 API의 기능 차이 및 반영 결과

| 기능                           | 기존 프론트                                          | API 문서와 반영 결과                                                                             |
| ------------------------------ | ---------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| 데이터 저장                    | 브라우저 메모리에만 저장, 새로고침 시 초기화         | 서버 목록·상세·등록·수정·삭제 연결                                                               |
| 게시 기간                      | 시작·종료 시각을 시·분까지 지정                      | `YYYY-MM-DD` 날짜만 지정, 시작일과 종료일 모두 포함                                              |
| 상태                           | 브라우저 현재 시각으로 계산                          | KST 날짜 기준 서버 `SCHEDULED`·`ACTIVE`·`ENDED` 사용                                             |
| 노출 순서                      | 1 이상, 중복·빈 번호 허용, 기본값은 최대값+10        | 0 기반 고유 순번. 등록은 0~N, 수정은 0~N-1. 신규 기본값은 전체 개수 N                            |
| 순서 변경 영향                 | 다른 팝업 순서는 유지                                | 삽입·이동하는 위치를 서버에 전달하고 결과를 다시 조회. 프론트에서 임의 재정렬하지 않음           |
| 관리자 목록                    | 노출 순서 오름차순, 전체 목록                        | 최신 등록순, 페이지당 10개와 페이지 이동                                                         |
| 수정 데이터                    | 목록의 로컬 데이터 사용                              | 목록에는 본문·이미지가 없으므로 상세 조회 후 편집                                                |
| 이미지                         | JPG·JPEG·PNG·GIF·WebP, 크기 제한 없음, 파일명만 보존 | PNG·JPEG·WebP, 최대 10MB, 실제 파일 업로드와 CDN 미리보기. GIF 제외                              |
| 본문·이미지 필수 여부          | 둘 중 하나 필수                                      | 각각 선택 항목으로 문서화되어 둘 다 없어도 입력 허용                                             |
| 본문 길이                      | 프론트에서 3,000자 제한                              | 문서에 글자 수 제한이 없어 해당 제한 제거. 전체 요청 15MB 초과 등 서버 오류는 표시하고 입력 보존 |
| 특정 날짜의 전체 팝업 미리보기 | 주석 상태, 미구현                                    | 해당 API 문서가 없어 추가하지 않음. 편집 중인 단일 팝업 미리보기는 유지                          |

`N`은 삭제되지 않은 전체 팝업 수이며 목록 페이지의 항목 수와 다르다. 내부 폼의 `bodyMarkdown`·`displayPriority` 필드는 요청 시 각각 `description`·`displayOrder`로 변환한다.

## 문서만으로 확정할 수 없는 사항

- 본문과 이미지가 각각 선택 항목이지만, 둘 다 비어 있을 때의 별도 콘텐츠 조건은 명시돼 있지 않다. 현재 프론트는 추가 필수 조건을 적용하지 않는다.
- 본문의 최대 길이와 사용자 앱의 마크다운 지원 범위는 명시돼 있지 않다. 기존 관리자 미리보기와 안전한 링크 검증은 유지한다. 사용자 앱의 실제 렌더링과 일치하는지는 별도 확인이 필요하다.
- 이미지 최적화 전에는 원본 CDN URL이 반환될 수 있다. 변환 완료까지 자동으로 재조회하는 별도 폴링은 제공하지 않는다.
- 등록 CSV의 `request` 설명에는 `startAt/endAt`이 남아 있으나 실제 필드 정의와 JSON 예시는 `startDate/endDate`로 일치하므로 후자를 사용한다.
- PATCH CSV는 필드를 정의하지만 multipart 파트 명세를 별도로 반복하지 않는다. 등록 문서의 `request` JSON + `image` 파일 구조와 수정 문서의 ‘request 파트’ 예시를 기준으로 동일 구조를 사용한다.
- 서버의 순서 재배치·동시 수정 처리와 실제 배포 상태는 실행 환경에서 확인이 필요하다.

## 검증

- API 계약 테스트: 엔드포인트·페이지 파라미터·JSON Blob·이미지 파일·본문/이미지 삭제·실패 응답.
- 페이지 테스트: 서버 정렬과 상태 유지·페이지 이동·등록·상세 편집·이미지 유지/삭제/교체·실패 재시도·삭제 후 이전 페이지 이동.
- 입력 테스트: 0 기반 순서 범위·날짜 경계·선택 콘텐츠·안전한 링크·이미지 형식과 10MB 경계.
- 공용 날짜 선택기 사용처 테스트: 팝업 날짜 입력·해제·외부 초기값 갱신, 시간 입력 제거.
